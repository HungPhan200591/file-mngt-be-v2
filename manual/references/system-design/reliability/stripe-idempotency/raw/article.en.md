# Designing robust and predictable APIs with idempotency

> Source: [Stripe](https://stripe.com/blog/idempotency)  
> Author: Brandur Leach  
> Published: February 22, 2017

Networks are [unreliable](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing). The networks connecting servers are more reliable than consumer last miles, but outages, routing problems and intermittent failures still happen. APIs and clients must remain robust during failure and bring a complex integration to a consistent state.

## Planning for failure

Consider a call between two nodes. The initial connection can fail while the client connects. The call can fail midway while the server is fulfilling the operation, leaving work in limbo. Or the call can succeed while the connection breaks before the server tells the client. Each case leaves the client uncertain. A connection failure before execution may be safe to retry, while a mid-operation failure is ambiguous. Even an API and one client are a distributed system.

## Making liberal use of idempotency

The easiest way to address inconsistent distributed state is to make server endpoints **idempotent**: they can be called any number of times while side effects occur only once. When a client sees an error, it can retry until it verifiably succeeds. For a DNS operation where the full desired record is in the request, repeated calls are safe; if the record already exists, the server can ignore the duplicate and return success.

According to HTTP semantics, [`PUT` and `DELETE` are idempotent](https://tools.ietf.org/html/rfc7231#section-4.2.2). [`PUT`](https://tools.ietf.org/html/rfc7231#section-4.3.4) creates or replaces the target with the request payload; a partial modification would conventionally use [`PATCH`](https://tools.ietf.org/html/rfc5789).

## Guaranteeing “exactly once” semantics

Some operations, such as charging a customer, must not happen twice. An **idempotency key** is a unique ID generated by the client for one operation and sent with the request. The server correlates that ID with its state. A retry with the same key can be processed safely.

For a connection failure, the retry may be the first request the server sees. For a failure during execution, the server completes or recovers the operation; if an ACID database rolled it back, retrying the whole operation is safe. For a response failure after successful execution, the server returns the cached successful result.

Stripe implements idempotency keys on mutating endpoints, including `POST`, using the `Idempotency-Key` header. A failed request can be retried with the same key without charging the customer twice.

## Being a good distributed citizen

Retrying safely is not enough; retries must also be considerate. A transient failure may disappear, but a server incident may persist, and retries can worsen degradation. Clients should use [exponential backoff](https://en.wikipedia.org/wiki/Exponential_backoff), waiting proportionally to `2^n` as failures increase.

Randomness should be added to the wait time. If many clients fail simultaneously, identical schedules can hammer the recovering server: the **thundering herd problem**. Random jitter spreads retries and gives the server room to recover.

The [Stripe Ruby library](https://github.com/stripe/stripe-ruby) retries with an idempotency key, increasing backoff and jitter. Its implementation is available [on GitHub](https://github.com/stripe/stripe-ruby/blob/1bb9ac48b916b1c60591795cdb7ba6d18495e82d/lib/stripe/stripe_client.rb#L78-L92).

## Codifying the design of robust APIs

Failure handling is essential to robust and predictable APIs. Client retry logic and server idempotency are useful techniques available in any technology stack:

* **Handle failures consistently:** clients should retry remote operations; otherwise state may remain inconsistent.
* **Handle failures safely:** use idempotency and idempotency keys so retries are safe.
* **Handle failures responsibly:** use exponential backoff and random jitter, and avoid overwhelming degraded servers.
